# Bundle signing and key rotation

## Modes and architecture

`CONTINUUM_SIGNING_MODE` accepts `unsigned`, `hmac`, or `ed25519`. Production must select the mode explicitly; Continuum never infers that configured development credentials mean production signing is enabled.

- `unsigned` is the default when `CONTINUUM_SIGNING_MODE` is absent, even if signing keys happen to be present in the environment. It writes no signature sidecar. If a run ID is reused, stale `bundle_signature.json` and `manifest.sha256` files are removed.
- `hmac` uses `CONTINUUM_SIGNING_KEY` (the legacy alias `CONTINUUM_BUNDLE_HMAC_KEY` is supported). The key must be present and contain at least 32 UTF-8 bytes when HMAC mode is selected; a missing or undersized key is an error and never silently downgrades to unsigned. Generate at least 32 bytes of cryptographically secure randomness; do not use a human password. HMAC is appropriate when both signing and verification happen in one trusted environment.
- `ed25519` signs with a private key and verifies with a separately configured public-key ring. The signature authenticates the manifest digest, algorithm, key ID, and creation time. Keys embedded in a bundle are informational and are checked against the trusted keyring; they are never trusted by themselves.

New signatures use version 2 canonical signing input. Existing HMAC version 1 signatures remain readable. Unbound legacy Ed25519 signatures are rejected because their key ID and creation time were not covered by the signature.

## Environment variables

| Variable | Purpose |
| --- | --- |
| `CONTINUUM_SIGNING_MODE` | Explicitly selects `unsigned`, `hmac`, or `ed25519`. Missing mode means unsigned, regardless of whether keys are present. |
| `CONTINUUM_SIGNING_REQUIRED` | Set to `true` to require an explicit `hmac` or `ed25519` mode and valid key configuration before any workflow starts. |
| `CONTINUUM_VERIFY_SIGNATURES` | Set to `true` (default) to verify signatures with `continuum verify`; set to `false` for an explicit policy-only check in development. It cannot be disabled when `CONTINUUM_SIGNING_REQUIRED=true`. Publishing still verifies signatures for its report. |
| `CONTINUUM_SIGNING_KEY` | HMAC secret. Store it in the deployment secret manager or GitHub Actions secrets. |
| `CONTINUUM_SIGNING_KEY_ID` | Identifier authenticated by new signatures; defaults to `default`. Use 1–128 ASCII letters, digits, `.`, `_`, `:`, or `-`, starting with a letter or digit. |
| `CONTINUUM_SIGNING_PRIVATE_KEY` | Ed25519 PKCS#8 PEM private key, supplied as a secret value. |
| `CONTINUUM_SIGNING_PRIVATE_KEY_FILE` | Path to an Ed25519 PKCS#8 PEM key mounted from a secret manager. |
| `CONTINUUM_ED25519_PRIVATE_KEY_B64` | Ed25519 32-byte raw private key, base64 encoded. |
| `CONTINUUM_ED25519_PRIVATE_KEY_PATH` | Path to a file containing the base64 encoded raw private key generated by `continuum keygen`. |
| `CONTINUUM_SIGNING_PUBLIC_KEYS_JSON` | Inline JSON trusted Ed25519 public-key ring. |
| `CONTINUUM_SIGNING_PUBLIC_KEYS_FILE` | Path to a JSON trusted Ed25519 public-key ring. |
| `CONTINUUM_SIGNING_PUBLIC_KEY` / `CONTINUUM_SIGNING_PUBLIC_KEY_FILE` | Legacy single public PEM key; the key ID must match `CONTINUUM_SIGNING_PUBLIC_KEY_ID` or `CONTINUUM_SIGNING_KEY_ID`. |
| `CONTINUUM_ED25519_PUBLIC_KEY_B64` / `CONTINUUM_ED25519_PUBLIC_KEY_PATH` | Legacy single raw public key in base64 form. |
| `CONTINUUM_INCLUDE_PUBLIC_KEY_IN_BUNDLE` | Set to `1` to copy the public key into a bundle for portability. Verification still requires the independently configured trusted key. Defaults to `0`. |

Do not set multiple private-key sources, multiple public-key sources, or both an Ed25519 ring and a legacy public key. Continuum rejects ambiguous or malformed configuration. It never writes private-key material into the evidence bundle.

HMAC values are UTF-8 text with a minimum encoded length of 32 bytes. The documented GitHub command below generates 48 random bytes represented as URL-safe text. Ed25519 raw private keys are exactly 32 bytes encoded as canonical base64; PEM private keys must be Ed25519 PKCS#8. Trusted ring public keys are exactly 32 raw bytes encoded as canonical base64. IDs follow the same character and length rules above. Keep private material in a secret manager or a local directory with owner-only access.

`CONTINUUM_SIGNING_REQUIRED=true` with a missing mode, an unsigned mode, or a missing/invalid key fails before Continuum creates the run directory or executes workflow steps. Explicit `hmac` or `ed25519` mode also fails before workflow execution when its key configuration is missing. In development and tests, omit the mode or explicitly set `unsigned`; an available key is ignored unless signing mode is selected.

`continuum verify` checks both the policy result and signature by default. In development, set `CONTINUUM_VERIFY_SIGNATURES=false` to check only the policy result for an unsigned run. Production or other required-signing environments reject this setting, so disabling a signature check cannot turn an unsigned run into a successful required-signing verification.

HMAC mode accepts one shared secret at a time. Replacing that secret makes older HMAC bundles unverifiable unless the old secret is restored; use Ed25519 and retain old public keys in the ring for overlapping verification during rotation.

## Public key ring format

The keyring is public configuration and may be distributed to verifiers. `notBefore` and `signUntil` constrain when a signature may have been created. `verifyUntil` controls how long a rotated or retired key remains trusted for historical bundles.

```json
{
  "version": 1,
  "keys": [
    {
      "keyId": "continuum-2026-09",
      "algorithm": "Ed25519",
      "publicKeyB64": "BASE64_ENCODED_32_BYTE_PUBLIC_KEY",
      "notBefore": "2026-09-01T00:00:00Z",
      "signUntil": "2027-03-01T00:00:00Z",
      "verifyUntil": "2028-03-01T00:00:00Z"
    }
  ]
}
```

During rotation, add the new public key and keep the old public key in the ring through its `verifyUntil` date. Set the old key's `signUntil` to the cutoff and give the new key its own `notBefore`/`signUntil` window. Once an old key's verification window expires, signatures from it fail verification. Unknown IDs, malformed keys, mismatched embedded keys, invalid timestamps, signatures outside their signing window, and future-dated signatures all fail closed.

## Owner action required for GitHub Actions

The repository's `.github/workflows/ci.yml` and `.github/workflows/continuum-e2e.yml` use the HMAC compatibility mode and require one GitHub Actions repository secret:

1. Generate a high-entropy value locally, for example `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
2. In `Deterministic-Operations-Platform/continuum`, open **Settings → Secrets and variables → Actions → Repository secrets → New repository secret**.
3. Name the secret exactly `CONTINUUM_SIGNING_KEY` and paste the generated value. Do not commit it or add it to a workflow file.

No signing secret is stored in this repository. Without that owner-provided secret, the GitHub run-and-verify jobs cannot produce or verify their HMAC-signed CI bundle. Unit tests generate ephemeral keys and do not need the repository secret.

For a production Ed25519 deployment, generate a keypair with `python -m continuum keygen --out-dir .continuum/keys`. This creates `.continuum/keys/continuum-ed25519.private.pem` and `.continuum/keys/continuum-ed25519.public.pem`; protect the private file with owner-only permissions and store it only in the deployment secret manager. Set `CONTINUUM_SIGNING_MODE=ed25519`, `CONTINUUM_SIGNING_REQUIRED=true`, `CONTINUUM_SIGNING_PRIVATE_KEY_FILE`, and `CONTINUUM_SIGNING_KEY_ID`. Put the public key's raw 32-byte value (base64 encoded) in the trusted ring supplied through `CONTINUUM_SIGNING_PUBLIC_KEYS_FILE`. Keep that ring outside the signed run bundle's trust boundary.
